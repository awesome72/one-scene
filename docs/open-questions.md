# 열린 질문 — 문서 간 불일치와 미정 사항

자료(기획안·구현 가이드·SKILL.md·목업·발표 자료)를 교차 검토하면서 찾은 것들.
각 항목은 **해당 Phase 착수 전에** 결정한다. 결정하면 `결정:` 줄을 채운다.

## A. 화면·디자인 (Phase 4 전)

### A1. 데스크톱 2열 vs 모바일 단일 열
- 기획안 8장: 왼쪽 대화 + 오른쪽 서사 아크 패널 (데스크톱 기준), 모바일은 하단 시트
- 목업: 390px 모바일 단일 열, 아크는 헤더의 5칸 표시
- 제안: 목업 기준 모바일 우선. 데스크톱에서만 오른쪽 패널 확장
- 결정: (2026-10-09, 잠정) 목업 기준 모바일 단일 열(최대 430px 가운데 정렬). 데스크톱 오른쪽 패널은 나중에

### A2. 교정 하이라이트 색
- 기획안: 노랑(상투어) / 주황(감정 명명) / 회색 점선(빈칸)
- 목업: 붉은 표시 한 색 + 번호, 선택 시 연한 붉은 배경, 종류는 하단 시트에서 구분
- 제안: 목업 방식 (색보다 번호와 질문이 주인공)
- 결정: (2026-10-09, 잠정) 목업 방식. 붉은 밑줄 + 번호, 빈칸은 점선 상자, 종류·이유는 하단 시트

### A3. 홈의 "새 글을 여는 질문" 순환
- 목업에 있지만 API 6장에 없음
- 제안: `GET /opening-questions` 추가 또는 `POST /sessions`에 `opening_question` 파라미터. 보관함의 "다음 글감"도 같은 경로로 시작
- 결정: (2026-10-09, 잠정) `GET /opening-questions` + `POST /sessions {opening_question}`로 구현. 질문 목록은 `backend/app/data/opening_questions.yaml`

## B. 데이터·엔진 (Phase 1, 3 전)

### B1. `topic_sentence`, `target_length`는 누가 채우나
- stage_machine 1단계 마감 조건이 둘을 요구하지만, extractor 출력 스키마에 없음
- 제안: 코치가 결정 질문을 던진 뒤, 사용자 답을 확정 UI(버튼)로 저장. 또는 extractor에 `topic_candidate`, `length_choice` 필드 추가
- 결정: (2026-10-09, 잠정) extractor가 사용자가 직접 말한 주제 문장(원문)과 길이 선택을 뽑아 비어 있을 때만 채운다. 사용자는 `PATCH /sessions/{id}`로 언제든 고친다

### B2. 사용자·인증
- `sessions.user_id`는 있지만 users 테이블과 인증 방식이 없음
- 제안: MVP는 users 테이블 + 이메일 매직링크(또는 베타 초대 코드). Phase 1에 최소 형태로 포함
- 결정: (2026-10-09 확정) Neon Auth(관리형 Better Auth) 이메일·비밀번호. 운영은 JWT 필수(JWKS EdDSA, iss·aud = Auth origin, sub = 사용자 ID, 15분 만료), 로컬·테스트는 `NEON_AUTH_BASE_URL`이 없으면 `X-User-Id`. 로그인 전 만든 세션은 옛 ID에 남아 보이지 않는다

### B3. 정서적 안전 신호
- 기획안 12장·SKILL.md 9장: 고통 신호 감지 시 진행 중단. 그러나 7장 파이프라인에 해당 단계 없음
- 제안: extractor 출력에 `distress: bool` 추가 → true면 질문 대신 상태를 묻는 고정 응답 + 넘어가기 제안
- 결정: (2026-10-09, 잠정) 제안대로. extractor `distress` → 질문 생성 없이 `data/fixed_replies.yaml`의 고정 응답

### B4. 재료 원문 규칙과 목업의 재료 카드
- 가이드: 재료 `text`는 사용자 발화의 **연속된 부분 문자열**
- 목업 재료 카드: "회의실이었어요. 창밖만 보고 있었어요." — 실제 발화의 중간 문장이 빠진 비연속 발췌
- 제안: 규칙 유지(재료 2개로 저장), 카드에서는 같은 블록 재료를 이어 표시. 공백·따옴표 정규화 규칙은 Phase 3에서 정의
- 결정: (2026-10-09, 잠정) 규칙 유지. 공백·따옴표 차이만 허용해 찾고, 저장은 발화 쪽 원문 표기로 (`extractor.find_verbatim`)

### B5. 교정 "그대로 두기"
- 목업 초안 화면에 [그대로 두기] 버튼 → 사용자가 무시한 지적을 저장할 곳이 없음
- 제안: `drafts.lint_result` 항목에 `dismissed: true` 추가, 4단계 마감 조건에서 제외
- 결정: (2026-10-09, 잠정) 제안대로. `drafts.lint_result` 항목에 `dismissed` 저장 (Phase 6에서 구현)

## E. 원본 문서 자체의 문제

### E1. SKILL.md 10장 예시가 철칙 1을 어김
- 마지막 코치 응답 "그 말을 처음 들었던 날은 어땠어요? 그때도 창밖을 봤어요?"는 물음표가 둘이다. 이 예시는 core.md로 모델에 그대로 들어가 "질문 두 개"를 학습시킬 수 있다
- 발표 자료는 이미 "그 말을 처음 들었던 날도 창밖을 봤어요?"로 고쳐 쓰고 있다. golden 테스트는 고친 문장을 쓴다
- 제안: SKILL.md 10장을 발표 자료 문장으로 고치고 `uv run python -m app.prompt_sync`
- 결정: (2026-10-09) 원본은 사용자 결정 대기. Phase 8에서 발표 자료 문장("…날도 창밖을 봤어요?")도 예/아니오 질문이라 검수기가 들쭉날쭉 탈락시키는 것을 확인 → golden은 "그 말을 처음 들었던 날, 창밖에는 무엇이 보였어요?"로 바꿈. SKILL.md 10장도 이 문장으로 고치기를 권장

## F. 실제 사용에서 본 품질 문제 (Phase 8 평가 항목)
- F1. ✅ (Phase 8: 프롬프트 + 서버 안전장치 `ensure_dialogue`, 대사 추출 80%→100%) 추출기가 따옴표 안의 대사("이번 분기만 버티자.")를 arc_block 없이(null) 저장하거나 놓친다 → 개요에 안 들어가고, 초안 교정에서 이미 한 말을 다시 묻게 됨
- F2. ✅ (Phase 8: 재료 카드에서 주제 문장 고치기·목표 길이 고르기) `topic_sentence`가 첫 발화("회사 그만둔 얘기를 쓰고 싶어요")로 정해지면 나중의 더 분명한 주제 문장으로 바뀌지 않음 (B1: 비어 있을 때만 채움). 화면에서 고치기(PATCH) UI 필요
- F3. ✅ (Phase 8: 인용 원문 규칙 검사, 85%→100%) 코치가 사용자 말을 인용하며 어미를 바꾼다 ("싸여 있었는데" → "싸여 있었다"). 인용이 원문 부분 문자열인지 검수 항목으로 둘지
- F4. (미해결) 같은 재료로도 초안마다 빈칸 수가 3~5곳으로 흔들린다
- F5. ✅ (Phase 8: 질문자·검수기 규칙 보강, 평가에서 해석 없음 100%) 검수기가 코치의 해석성 반응을 통과시킨다 ("고기를 굽는 것과 집게를 들고 있는 것 사이에 틈이 느껴져요" — 사용자 대신 의미 부여, 철칙 3). `no_summary_or_advice` 판정 기준 보강 필요
